GIT

Git — это система контроля версий. С помощью Git можно создавать различные версии своего кода, просматривать историю изменений проекта и восстанавливать предыдущие версии кода.

Установливается Git с официального сайта. После установки появится терминал Git Bash.

*Терминал - это программа, которая позволяет пользователю взаимодействовать с компьютером с помощью текстовых команд.

Настройка

Перед началом работы нужно настроить имя пользователя и почту. Для настройки имени вводим: git config --global user.name ваше_имя

--global - это флаг (иногда называется опция), которое говорит о том что команда будет выполненна на глобальном уровне.

Аналогичная команда для электронной почты:git config --global user.email адрес вашей почты

Чтобы проверить введенные данные, используйте команду: git config --global --list Эта команда выведет список всех глобальных настроек Git.

Файловые команды

Существует два способа указать путь к папке/файлу, это абсолютный и относительный путь. Абсолютный путь — это полный, уникальный адрес к файлу или папке, начинающийся от корневой директории. Относительный путь — это адрес относительно текущего местоположения.

Команда Что делает
pwd Узнать полный путь к текущей папке
cd название_папки Перейти в выбранную папку
cd .. Переместиться на одну папку назад
cd / Переместиться в корневую папку
cd - Вернуться к предыдущей рабочей папке
cd ~ Перейти в домашнюю папку пользователя
ls Показать файлы и папки в текущей директории
start . Открыть текущую папку в файловом менеджере
code . Открыть текущую папку в VS Code
touch index.html Создать файл index.html
mkdir project Создать папку с именем project
rm имя_файла Удалить файл
rmdir имя_папки Удалить пустую папку

Создание репозитория

Создать репозиторий можно двумя способами:
- Создать репозиторий на вашем компьютере (локально), а затем соединить его с удаленным репозиторием на GitHub;
- Создать удаленный репозиторий на GitHub, а затем клонировать его на ваш компьютер.

Создать локально:

  1. Вводим команду git init
  2. Создаем удаленный репозитрий на ГитХабе
  3. Связываем локальный репозиторий с удаленным git remote add origin [ссылка на репозиторий]
  4. Связываем локальную ветку с удаленной и отправлем с неё данные: git push -u origin main

*origin — это не команда, а имя основного удалённого репозитория. Оно может быть любым, но принято называть именно так

*Флаг -u это сокращение от --set-upstream

Создать удаленно:

  1. Создаем репозиторий на гитхабе. Чтобы репозиторий не был полностью пустым, рекомендуется отметить опцию создания файла `README.md`. Этот файл используется для описания проекта
  2. Нажимаем нопку < > Code и копируем ссылка проекта
  3. В терминале вводим команду git clone [скопированная ссылка]

Так как репозиторий клонируется, то связь устанавливается как с репозиторием, так и с веткой/ветками

Коммит

Коммит — это фиксация истории проекта.
Систему Git можно представить как дерево с множеством веток, причём каждая ветка состоит из множества коммитов.

"Главная ветка" — это исходная ветка, которая создаётся автоматически при инициализации репозитория. Ветки исходящие от неё будут содержать всю информацию главной ветки до момента ответления.

Git позволяет нам перемещаться по веткам и их коммитам, откатывать историю назад, создавать новые ветки из любой точки истории.

Чтобы всегда знать, где мы находимся, существует указатель HEAD. Это указатель нашего текущего положения, или точнее, указатель текущей ветки и определённого коммита, который может стать родителем следующего. Когда мы хотим вернуться к старому коммиту, мы перемещаем этот указатель к нужному коммиту. Во всех других случаях он будет указывать на последнюю ветку, которую мы создали, и на последний коммит.

Статус файлов

Файлы могут иметь статус отслеживаемые(Tracked) и неотслеживаемые(Untracked). Отслеживаемые файлы могут находиться в трёх состояниях:

  1. Изменённые (Modified)
  2. Неизменённые (Unmodified)
  3. Подготовленные (Staged)

Чтобы узнать текущий статус файлов, используйте команду: git status

Если выводятся файлы, выделенные красным — значит есть новые изменения, которые не добавлены. Иначе говоря — есть не отслеживаемые Git файлы.

Если файлы выводятся зеленым — недавно измененные файлы добавлены. Иначе говоря — все файлы отслеживаются Git.

Если нет подсвеченных файлов и надпись такого плана: "nothing to commit, working tree clean" — значит новых не внесенных изменений нет. Все файлы отслеживаются Git.

Помимо команды "status", состояние файлов можно узнать с помощью VS Code в проводнике или во вкладке Гит. У неотслеживаемых файлов будет стоять буква "U", а у измененных "M"

Для того чтобы сохранить новое состояние файлов, их нужно проиндексировать, то есть отправить в обслать Staging Area. Для этого используем команду git add [имя_файла.расширение], если хотим проиндексировать конкретный файл, либо команду git add -A, которая проиндексирует все измененные файлы.

Поиндексировать файл также можно во вкладке гит в VS Code, нажав плюс напротив файла, либо нажав плюс в графе изменения, тогда все перечисленные файлы будут проиндексированы.

После индексации, нужно провести фиксацию (закоммитить), то есть отправить данные в локальный репозиторий, и создать запись в истории проекта. Используется команда git commit -m "описание коммита"(кавычки обязательно), либо нажав кнопку "Фиксация" во вкладке Гит в редакторе, предварительно написав сообщение в графе над кнопкой.

Отмена|изменения

git restore index.js или git checkout index.js(старая команда) - удалит все новые непроиндексированные изменения. Данная команда аналогична кнопке "отменить изменения" в вкладке гит в редакторе кода.

git restore --staged index.js или git reset HEAD index.js(устаревшая) отменит индексацию. Аналогично кнопке "отмена промежуточного изменения" в редакторе. Ничего не удаляет.

git revert HEAD - удалить последний коммит, то есть проект вернется к состоянию предпоследнего коммита. При этом команда не удаляет историю, а создает новый коммит. Таким образом, данные удаленного коммита будут всегда доступны для работы и восстановления

Так как создается новый коммит, то нам потребуется ввести к нему сообщение, поэтому быстрая команда git revert HEAD откроет VIM-редактор, где нам потребуется ввести сообщение, чтобы этого избежать можно ввести сообщение сразу git revert HEAD -m "Отмена последнего коммита" или воспользоваться командой git revert HEAD --no-edit тогда сообщение к коммиту создатся по умалчанию.

git reset --hard HEAD - удаляет последний коммит, команда аналогичная revert, только данные удаляются полностью, также коммит удаляется в истории проекта. Опасно, особенно если работаете с удаленным репозиторием.

git revert HEAD~n..HEAD - откатит проект на n коммитов назад, и создаст столько же коммитов отмены в истории. Например, у нас есть коммиты A B C D E, и мы хотим вернуть изменения в проекте на два коммита назад, к коммиту C - git revert HEAD~2..HEAD

git reset HEAD~n - откатит проект на n коммитов, удалит коммиты из истории, но все измененния останутся, но будут непроиндексированы.

Происходит это потому что reset имеет 3 режима работы: --mixed, --soft, --hard

--mixed - стоит по умолчанию. Без сокращения команда выглядит так git reset --mixed HEAD~2 и аналогична git reset HEAD~2

--soft - также откатить проект назад, но все измененные данные будут проиндексированны

--hard - откатит проект назад, и все данные будут удаленны.

Вместо указателя HEAD/HEAD~n можно использовать хэш коммита. Данный способ более точный в отличие от относителньой ссылки HEAD

Изменить сообщение коммита

git commit --amend -m "Новое сообщение коммита" - изменит сообщение последнего коммита

git rebase -i [хэш коммита] или git rebase -i HEAD~n - откроется VIM-редактор. Чтобы изменить сообщение нужно:

  1. Нажать i и войти в режим вставки (Insert mode);
  2. Изменить pick на r. Стираем слово pick и вводим r;
  3. Нажать Esc - выйти из режима вставки;
  4. Нажать : (двоеточие) - войти в командный режим;
  5. Ввести wq - сохранить и выйти;
  6. Нажать Enter

Удаление файлов

git rm index.js - удалит файл.Работает аналогично, как если удалить файл через проводник.

git rm --сached index.js - удалит файл из репозитория, и перестанет его отслеживать, но физически он останется в рабочей области.

Просмотр коммитов

git log - посмотреть историю всех коммитов. Выведет полный хэш коммита, автора, дату, сообщение коммита. Для выхода из меню коммитов,нажать на q.

git log --oneline - выведет сокращенный хэш коммитов и сообщения коммитов.

git show - информация о последнем коммите, в том числе о том что было измененно в проекте

git show [хеш коммита] - посмотреть инормацию по конкретному коммиту. Хэш коммита можно узнать через ранее показанные команды, либо в редакторе во вкладке Гит. Навести курсор на нужный коммит, справа всплывет окно по коммиту, внизу слева будет его хэш.

git diff - покажет непроиндексированные изменения.

git diff --staged - покажет проиндексированные изменения.

Любые изменения в проекте, будут отдельно отображаться в редакторе во вкладке Гит. Для этого нужно нажать на конкретный файл, в том числе доступны и файлы коммитов, откроется окно с кодом, где будут выделенны все изменения в коде.

Работа с ветками

Ветка - это указатель на существующий коммит, который который позволяет вести независимую линию разработки.

Новая ветка - это указатель на определенный коммит, для независимой разработки. При этом в новой ветке сохраняется связь с прошлыми коммитами.

Важно понять, что новая ветка ничего не копирует, а лишь ссылается на существующий коммит, что позволяет вести независимую разработку, фиксируя её прогресс новыми коммитами.

git branch [имя ветки] - для создание ветки.

git switch [имя ветки] или checkout [имя ветки] (устаревшая) - для перехода на ветку.

git switch -c [имя ветки] или git checkout -b [имя ветки](устаревшая) - для создание и перехода на новую ветку.

git branch - для просмотра всех имеющихся веток.

git branch -m [новое имя ветки] - для переименованя текущей ветки.

git branch -d [имя ветки] удалить ветку. При удаление ветки вы не должны на ней находиться.

Просматривать список всех веток, переходить по ним, создовать новые можно с помощью редактора кода нажав кнопку веток Гит.

Слияние веток

Слияние - это операция объединения изменений из одной ветки в другую. В зависимости от истории веток происходит:

  1. Fast-forward слияние - перемотать указатель ветки:
    • Когда: Целевая ветка не изменилась после создания сливаемой ветки
    • Что происходит: Указатель целевой ветки просто перемещается вперёд
    • Коммит слияния: Не создаётся
    • История: Остаётся линейной
  2. recursive merge - создать новый коммит слияния, объединяющий расходящиеся истории:
    • Когда: Обе ветки изменились после разделения
    • Что происходит: находит общий коммит до разветления, сравнивает, объединяет изменения
    • Коммит слияния: Создаётся
    • История: Становится нелинейной
  3. Слияние с конфликтами
    • Когда: Git не может автоматически объединить изменения
    • Что происходит: Процесс останавливается, требуя ручного разрешения
    • Вы разрешаете конфликты вручную
    • После git add и git commit создаётся коммит слияния

git merge [название ветки, которую сливаем] - команда слияние ветки. При этом вы должны находится в ветке в которую планируете слить

git merge -m "сообщение для коммита слияния" [название ветки, которую сливаем] - совершить слияние и указать сообщение к коммиту слияния. В случае если сценарий слияния - recursive merge. Если не указать сообщение, то откроется VIM-редактор, где вам нужно будет его написать.

git merge --abort - отменить слияние. Работает если не был совершен коммит.

Перебазирование

Rebase (перебазирование) это альтернатива слиянию, которая переписывает историю коммитов, перемещая изменения одной ветки на верх другой ветки.

Принцип работы:

  1. Находит общего предка двух веток
  2. Вычисляются патчи (изменения) каждого коммита текущей ветки
  3. Текущая ветка перемещается на конец целевой ветки
  4. Патчи применяются последовательно, создавая новые коммиты поверх целевой ветки.
  5. Оригинальные коммиты остаются в объектной базе Git, но становятся недостижимыми".

git rebase [ветка слияния] - перебазирование.

Преобразование делает дерево коммитов более линейным и красивым. Но оно не всегда уместно.

Если ветка является публичной. Переписывание общих веток будет мешать работе других членов команды. Также когда важна точная история коммитов ветки (так как команда rebase переписывает историю коммитов).

git rebase --abort - отменить перебазирование.

git rebase --continue, git rebase --skip , git rebase --quit - продолжить после разрешения конфликта, пропустить текущий коммит, прервать, но оставить изменения. Команды при конфликте, их аналоги имеются в VS Code.

Создание ветки от коммита

git checkout -b [название новой ветки] [хеш коммита] - создаст новую ветку от указанного коммита

Вместо хэша можно использовать относительную ссылку git checkout -b [название новой ветки] HEAD~5 (создать ветку от 5 коммита назад)

Скопировать изменения из коммита

git cherry-pick [хеш коммита] - копирует изменения из указанного коммита любой ветки. Создается новый коммит.

git cherry-pick --abort - отменить cherry-pick

git cherry-pick -n [хеш коммита] - применить изменения, но не создавать коммит.

it cherry-pick abc123 -m "Новое сообщение коммита" - позволяет изменить сообщение коммита. По умолчанию сообщение коммита будет таким же как у копируемого коммита.

git cherry-pick -x - добавляет в сообщение "cherry picked from commit abc123def456...". Укажет откуда был копираван коммит.
